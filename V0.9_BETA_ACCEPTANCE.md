# SI Grid Monitor V0.9.0 beta acceptance

This report audits the implementation at the V0.9 beta branch against the
unchanged `SPECIFICATION.md` V1.1 baseline. A source file, test stub, or passing
unit test is not treated as real Home Assistant acceptance.

Status vocabulary:

- **Implemented** — production code and user-facing behavior exist.
- **Automated-test verified** — behavior is exercised without a real HA instance.
- **Manual-test pending** — implementation exists but requires a clean, real HA test.
- **Unsupported** — deliberately not implemented in this beta.
- **Failed** — implemented behavior is known not to meet the requirement.

## Safe upgrade from V0.8

1. Create a full Home Assistant backup. Separately preserve the SI Grid Monitor
   database and matching `-wal`/`-shm` files while HA is stopped.
2. Record current integration entry IDs, source entity/polarity, contracted-power
   periods, tariff policy, smoothing and forecast horizon.
3. Install the V0.9 beta through HACS, restart HA, and hard-refresh the browser or
   reopen the companion app. Do not delete the integration entry.
4. Confirm the manifest/panel version is `0.9.0`, the existing entry loads, and
   oldest/newest archive timestamps and row counts match the pre-upgrade values.
5. Check the current source, B1-B5 schedule, latest completed quarter and one old
   exact UTC quarter. Confirm no historical target or rule provenance changed.
6. Reload the entry and restart HA once more. Check that only one sidebar panel,
   one entity set per entry, and no duplicate quarter row exist.

V0.9 keeps archive schema 6. No migration, recalculation, purge, or historical
classification is introduced by this branch.

## Backup and rollback

- Back up `.storage/si_grid_monitor_<entry_id>.db` together with its WAL/SHM
  companions while Home Assistant is stopped. HA backups should also be tested,
  not assumed.
- To roll back code, stop HA, restore the V0.8 integration files and the matching
  pre-upgrade database copy, then restart and clear the frontend cache.
- Never copy only the main DB while an active WAL may contain committed data.
- Do not use HACS removal as a database reset. Code removal must leave the archive
  untouched. There is no V0.9 factory-reset action.
- Recorder reconstruction creates its own SQLite backup, but that is not a
  substitute for a complete HA backup.

## Clean Home Assistant beta procedure

Use a disposable HA instance and a synthetic signed-power sensor; do not use the
production archive for destructive lifecycle checks.

1. Add the repository to HACS, install V0.9, restart HA and complete setup using
   positive-import Mode A plus a dated B1-B5 assignment.
2. Confirm one **SI Grid Monitor** sidebar item and the expected entity set.
3. Exercise import, export, measured zero, unavailable, stale, recovery, a quarter
   rollover and three exceeded quarters. Confirm archive/API/dashboard agreement.
4. Check all seven pages in English and Slovenian at desktop, tablet and Android
   widths, light/dark themes, keyboard and touch. Include 92/100-quarter DST days.
5. Add a second entry and prove live data, WebSocket responses, archive files and
   history never cross entry IDs.
6. Reload each entry and restart HA during a quarter and immediately after a
   boundary. Verify checkpoint recovery, one finalized row and no task warnings.
   Also interrupt an in-progress setup/reload once; confirm cancellation is
   propagated, no sensor/binary-sensor entity or listener remains orphaned, and
   a subsequent setup succeeds without deleting the archive.
7. Upgrade from a preserved V0.8 fixture. Compare configuration, entity unique
   IDs, schema, row counts, historical targets, source epochs and tariff versions.
8. Remove only the HACS code, verify the archive remains, reinstall the same beta,
   re-add/reload safely and confirm history returns without duplicate rows.
9. Simulate WebSocket disconnect/reconnect and temporary SQLite lock/read-only
   failures. Confirm useful errors, retry, and no corrupted or fabricated values.
10. Preserve logs, screenshots and before/after database counts as acceptance
    evidence. Do not mark HA-verified based only on this checklist.

## Beta blockers and remaining risks

The branch is suitable for review but is **not release-ready** until the clean HA
procedure provides evidence for installation, reload/restart, HACS lifecycle,
mobile rendering, bilingual accessibility, Recorder integration and database
failure recovery. Modes B-E and factory reset remain explicit V1 gaps. Official
HACS listing and Pages publication are external, unauthorized release activities.

Lifecycle tests use a deliberately narrow simulated Home Assistant surface.
They verify deterministic rollback, both partial forwarding orders, retry and
best-effort durable shutdown. They are not evidence that Home Assistant itself
was installed or that its platform-forwarding implementation was acceptance
tested. The managed Windows runner cannot create asyncio's internal socketpair,
so real-event-loop cancellation cases are skipped there and execute in Linux CI;
the immediate cancellation paths remain covered on every platform.

Shutdown cancellation is propagated after durable cleanup finishes or after a
10-second grace period. If that bound expires, cleanup continues in its tracked
task and the runtime remains registered; a later unload joins the same task.
This avoids indefinite HA shutdown blocking without claiming that an active
archive has already been removed.

Setup applies the same ownership boundary. A prior same-entry runtime must report
durable shutdown complete before its registry and `runtime_data` references can
be replaced. Setup waits at most 10 seconds, then asks Home Assistant to retry;
it never opens a second runtime over an archive still owned by the first one.
